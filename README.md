# XDE-SINDy

**XDE-SINDy** is an explainable, dimension-aware surrogate-assisted differential-evolution framework for high-dimensional expensive single-objective system optimization.  The repository contains the complete algorithm implementation used in the manuscript and a reduced-order underwater-welding robot digital-twin validation.  Benchmark comparison runners, generated result files, and manuscript figures are intentionally excluded so that the repository remains a small, reproducible source release.

## Installation

The CPU implementation needs Python 3.10 or newer, NumPy, SciPy, and scikit-learn.  For the GPU/EvoX path, install a CUDA-enabled PyTorch build first, then install:

```powershell
python -m pip install -r requirements-evox.txt
python -m pip install -r requirements-gpu.txt
```

`cupy-cuda12x[ctk]` must match the CUDA runtime used by the PyTorch installation.  The algorithm can still be imported without EvoX; `evox_adapter.py` raises a clear error only when the EvoX boundary is actually used.

## Direct XDE-SINDy use

The core class is `algorithms.xde_sindy.XDESindy`.  The objective is a scalar callable, and `bounds` is an array-like collection of `(lower, upper)` pairs.  All true objective calls are counted by the engine.

```python
import numpy as np
from algorithms.xde_sindy import XDESindy

dimension = 30
bounds = [(-5.12, 5.12)] * dimension

def sphere(x):
    return float(np.sum(np.asarray(x, dtype=float) ** 2))

optimizer = XDESindy(
    objective=sphere,
    bounds=bounds,
    population_size=30,
    max_evaluations=300,
    relative_improvement_mode="auto",
)
result = optimizer.minimize()
print(result.fun, result.x, result.evaluations)
```

The returned result contains the best decision vector, objective value, evaluation count, convergence history, and the white-box audit generated by the sparse model.  Use `optimizer.explain(result.x)` when an explicit term-level explanation is required.

## EvoX integration

`algorithms.xde_sindy.evox_adapter` provides three integration objects:

* `EvoXProblemAdapter` wraps a Torch batch evaluator as an EvoX `Problem`;
* `EvoXObjectiveBridge` sends each true-evaluation batch to EvoX and transfers the CUDA result to the XDE-SINDy backend with DLPack;
* `EvoXXDESindy` exposes the existing FE-driven engine as an EvoX `Algorithm`.

The integration preserves XDE-SINDy's archive, sparse-model fitting, uncertainty calculation, candidate selection, and true-FE accounting.  A minimal workflow follows the same boundary used in the paper:

```python
import torch
from evox.workflows import StdWorkflow
from algorithms.xde_sindy import XDESindy
from algorithms.xde_sindy.evox_adapter import (
    EvoXObjectiveBridge, EvoXProblemAdapter, EvoXXDESindy,
)

device = torch.device("cuda")
dimension = 30
bounds = [(-5.12, 5.12)] * dimension

def evaluate(batch):
    return torch.sum(batch * batch, dim=1)

bridge = EvoXObjectiveBridge(device=device)
engine = XDESindy(
    objective=bridge,
    bounds=bounds,
    population_size=30,
    max_evaluations=300,
    gpu_objective=True,
)
algorithm = EvoXXDESindy(engine, bridge)
problem = EvoXProblemAdapter(evaluate, dimension)
workflow = StdWorkflow(algorithm, problem, device=device)
workflow.init_step()
print(workflow.algorithm.result.fun)
```

For a CPU-only environment, instantiate `XDESindy` directly and omit the EvoX adapter.  The EvoX bridge requires EvoX 1.4 or newer, CUDA-enabled PyTorch, and a compatible CuPy runtime.

## Underwater-welding digital-twin validation

Both engineering scripts are parameter-free for direct IDE execution.  Edit the `RUN_*` constants at the top of `experiments/underwater_welding_simulation.py` when a different repeat count or budget is needed; no command-line switches are required.

```powershell
python experiments/underwater_welding_simulation.py
python experiments/underwater_welding_report.py
```

The first script writes `data/underwater_welding_comparison.csv` and a model manifest.  The second script reads that CSV and writes the median/IQR table, Friedman analysis, Holm-adjusted pairwise table, and publication figures into `data/underwater_welding_report/`.  The digital twin is explicitly marked as calibration-required: its robot geometry, thermal coefficients, porosity relation, and target bead dimensions must be identified with measured underwater-welding data before a physical deployment claim.

## Reproducibility and scope

The source release contains the complete XDE-SINDy algorithm and the engineering validation path.  It does not contain comparison-algorithm implementations, benchmark result spreadsheets, generated CSV files, or manuscript build products.  These exclusions avoid mixing the release package with intermediate experimental artifacts and keep the algorithm auditable.
